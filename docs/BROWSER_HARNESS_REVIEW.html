一、结论摘要

整条链路是通的：模型 tool_call（mcp__wanxiang-browser-bu__browser_*__<hash>）→ ToolExecutor(MCP) → McpManager → McpHttpTransport → 回环 HTTP 127.0.0.1:8787/mcp → McpServerRuntime → BrowserMcpTools → AndroidInAppBrowserEngine → WebView。内置 server 配置已写入 BuiltinMcpPresets（id=wanxiang-browser-builtin，默认启用），UI 与 harness 共用同一 BrowserRegistry 实例，设计正确。

但当前实现有几个会实际咬人的坑：最严重的是 browser.snapshot 的快照异步发布竞态（首次拿空、之后滞后）；其次是审批风险矩阵完全没落地（安全闭环缺失）与脱敏层未接线（敏感数据可能回灌模型）。多 tab 场景下有全局状态串扰；离屏 tab 截图大概率空白。

三、问题明细

🔴 高危（建议优先处理）

高危#1 browser.snapshot 返回滞后 / 首次为空（时序竞态）

位置：AndroidInAppBrowserEngine.snapshot()（L63-68）、SnapshotBuilder.refresh()（L37-67）

SnapshotBuilder.refresh() 里 scope.launch { eventBus.publish(SnapshotUpdated) } 是异步发布；而 engine.snapshot() 在 refresh() 返回后立即读 eventBus.snapshot.value。snapshot 调用发生在 CIO 线程（非主线程），Main.immediate 会异步派发 → refresh 返回时快照还没写进 bus → 返回的是上一次快照；首次调用直接返回空 PageSnapshot("...","empty",{})。onPageFinished 里那次同步 publish 掩盖了多数场景，但动态页面/并发时内容会与本次扫描不一致。

影响：模型第一次 snapshot 拿不到 refs；click/type 引用不存在的 ref 全部失败，是驱动链路最直接的阻断点。

建议：refresh() 直接返回 PageSnapshot；或 snapshot() 先 await publish 完成再取值；并去掉 click 回调里对 snapshot 的重复全量扫描。

高危#2 审批风险矩阵完全没落地（安全闭环缺失）

位置：ApprovalPolicyEngine.decide()（L94）、BrowserMcpTools.TOOLS（risk 字段无人消费）

设计文档 §4 承诺 snapshot/screenshot/current_url 等 LOW 免审、open MEDIUM 需审、click HIGH、evaluate/cookies_get CRITICAL+二级确认。实际 HarnessTool.MCP → 一律 ApprovalDecision(true, "high")：ASSISTED/REQUEST 模式下所有 MCP 工具（含只读的 snapshot）都要人工审批；反过来 FULL_ACCESS 下 evaluate（页内 JS 注入）、cookies_get 也全部自动放行。另外 browser.evaluate 没有检查 BrowserPreferences.allowEvalJs（默认 false）开关。

影响：要么模型每读一次页面都被打断（体验崩），要么用户干脆开 FULL_ACCESS 全放行（evaluate/写 cookie 无拦）。安全设计形同虚设。

建议：在 decide() 里解析 rawToolName + args 反查工具 risk 表，按 risk 档位决定放行/审批/二级确认；evaluate 必须尊重 allowEvalJs。

高危#3 SecretRedactingInterceptor 定义了但没接线

位置：runtime/browser/.../secret/SecretRedactingInterceptor.kt（无调用点）；BrowserMcpTools.cookies_get；NetworkInterceptor.onRequestStart（L31 原样存请求头）

cookies_get 直接返回 document.cookie；page_source 原样返回 HTML；CapturedRequest 把含 Authorization/Cookie 的 requestHeaders 原样存内存。唯一兜底是 ToolExecutor 最外层对 output 的 SecretRedactor.redact()，但那是面向 Linux 环境 secrets 的通用规则，不可靠。设计承诺的"Cookie/Authorization 默认脱敏"浏览器侧没实现。

影响：用户的会话 Cookie / Authorization 头 / 页面敏感值可能直接回灌给 LLM。

建议：在 cookies_get / page_source / console / network_list 出口统一过 SecretRedactingInterceptor.apply()。

高危#4 "外接桌面 AI"能力是死代码（未接线）

位置：BrowserMcpBootstrap.bootstrap()（L58 写死 loopbackOnly=true, token=null）；builtInConfig()（无调用方）；BuiltinMcpPresets（L163-173 写死 127.0.0.1:8787）

设计文档承诺允许 0.0.0.0:8787 + Bearer Token 供桌面 Claude/Cursor 通过 adb reverse 接入。实际 bootstrap 不读 allowRemoteConnect 偏好、不生成 token，builtInConfig(allowRemote=...) 定义了但从无调用方，与 presets 里写死的 127.0.0.1 配置重复。

影响：外接功能从未生效；两处配置未来可能漂移。

建议：bootstrap 按 prefs 决定绑定 host + 生成 token；删除 builtInConfig 死代码，配置统一以 BuiltinMcpPresets 为唯一来源。

🟠 中危（多 tab / 并发 / 性能）

中危#5 BrowserEventBus 全局单值 → 多 tab 串扰

位置：BrowserEventBus（url/title/snapshot 为全局 StateFlow）；BrowserMcpTools.current_url/title；engine 的 storage 类工具用 activeTab()

url / title / snapshot 不分 tab，任何 tab 导航都会覆盖全局值。browser.current_url / title 不看 tab 参数；browser.snapshot(tab=t1) 可能返回全局里 t2 的最新快照；cookies/local/session 系列全部操作 activeTab() 而非传入 tab。

建议：eventBus 状态按 tabId 分片（Map<tabId, State>），工具按 tab 参数取；storage 工具改用 tokenOf(args, engine)。

中危#6 click/type/press 嵌套 runBlocking + 每次全量重扫 DOM

位置：BrowserMcpTools.handleWithRef / handleType / handlePress（L106-134）；click 回调（L117-118）

在已经 runBlocking 的 CIO handler 里再次 runBlocking 包 suspend 调用（阻塞线程）；且 ref→selector 的回调每次都重新执行 engine.snapshot() 全量注入扫描脚本（又触发 #1 竞态），而不是从 RefResolver 缓存读。selector 依赖 DOM 里残留的 data-wanxiang-ref 属性，SPA 重渲染后失效。

建议：invoke 全程纯 suspend（去掉内层 runBlocking）；selector 从 SnapshotBuilder 缓存表读取，不要每次重扫。

中危#7 refMap 非线程安全

位置：SnapshotBuilder.ResolverRegistry（L102-109，普通 HashMap，跨协程写）

evaluateJavascript 返回后代码继续在 CIO 线程执行，多个 tab/并发 snapshot 会在不同线程同时 put 同一个 HashMap → 数据竞争（扩容可能损坏/死循环）。

建议：换 ConcurrentHashMap，或把写操作集中到主线程/加锁。

中危#8 快照文本 Unicode 反转义不完整

位置：SnapshotBuilder.unwrap()（L69-77）

只处理 \" \n \\，不处理 evaluateJavascript 返回的 \uXXXX。中文 / emoji / 特殊字符的按钮文案会以 \u767b\u5f55 这种转义字面量呈现给模型，影响可读性和判断。

建议：直接用 Json.parseToJsonElement 解析返回值，或用 java.net.URLDecoder / 正则解码 \uXXXX。

中危#9 离屏 tab 截图可能空白

位置：ScreenshotRecorder.capture()（L42-54）；feature/browser/BrowserScreen 只 embed 当前 active tab

view.draw(canvas) 软渲依赖 WebView 已 layout 且有尺寸。harness 打开的非 UI 显示 tab（无父容器、宽高 0 → fallback 1080×1920 硬画）大概率渲染空白或异常。

建议：截图前确保 view 有尺寸（临时 attach / measure），或截图瞬间把目标 tab 设为 active 并等一帧；v1.1 换 PixelCopy（需宿主 Window）。

🟡 低危（行为瑕疵 / 清理项）

低危#10-#16 其余问题

  • #10 browser.console_clear 空实现（L77）：返回 ok 但不清 eventBus 的 console。
  • #11 domFingerprint = UUID.randomUUID()（SnapshotBuilder L63）：每次随机，模型端无法据此判断"页面是否变化"。
  • #12 postMain / JsEvaluator 超时后副作用仍会执行（engine L239-245、JsEvaluator L17-34）：2s/5s 放弃等待但主线程 block 稍后照常执行，状态不确定；evaluateJavascript 死循环无取消机制。
  • #13 WebView cleartext 未配置（AndroidWebViewFactory）：跟随 app 全局 networkSecurityConfig，http:// 页面可能打不开（设计承诺的 localhost/白名单域 cleartext 未实现）。
  • #14 McpServerModule 里 prefs = BrowserPreferences.DEFAULT 写死：用户的 homeUrl / allowEvalJs / allowRemote / desktopUA 偏好不会传导到工具层。
  • #15 builtInConfig() 死代码：与 BuiltinMcpPresets 配置重复，未来易漂移（同 #4）。
  • #16 McpServerRuntime：runBlocking 包整个 JSON-RPC（CIO 线程被阻塞，并发受限） —— 该条不成立：POST /mcp handler 为 suspend 直接 await，未使用 runBlocking（复核确认，本条降为“小瑕疵”档）；notifications/initialized 返回 method-not-found（客户端忽略，但会留脏日志）；bootstrap 幂等不校验"运行中的 server 是不是浏览器 server"。

五、建议修复优先级

  • P0：#1 snapshot 竞态（先让模型第一次就能拿到 refs，否则整条链路不可用）。
  • P0：#3 脱敏接线（cookies/headers 是敏感数据）。
  • P1：#2 审批风险矩阵落地（按工具名分档 + evaluate 尊重 allowEvalJs）。
  • P1：#5 多 tab 状态分片（当前单 tab 可用，多 tab 会错乱）。
  • P2：#6/#7/#9（性能与并发）、#4（外接能力按需接或删）、其余低危项清理。
